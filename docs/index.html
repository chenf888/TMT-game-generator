How a game gets made

Every run follows the same measured pipeline. Nothing skips a stage, and nothing ships before the checks pass.

01
Interview
Seven questions lock theme, scale, natural ceilings, pacing, side content, and language. The theme dictates the tree, not just the names.
02
Design brief
A layer-by-layer table filled from measured blueprints and balance defaults, self-checked against nineteen rules before any code exists.
03
Scaffold
A fresh TMT v2.7 game folder with a permanent savefile id, patched and syntax-verified by a bundled script.
04
Generate
Decimal-safe layer code: upgrades with varied effects, milestones, challenges, buyables, automation ladders, softcaps, theming.
05
Check
58 static rules run over the source. Every FAIL is a blocker; every WARN needs a written justification in the brief.
06
Balance
Era-by-era reachability math against the measured heuristics, with every compounding multiplier zone audited.
07
Hand off
You serve the folder, play it, and verify the checklist: clean console, working saves, reachable endgame.

Every number came from a real game

The balance data is not intuition. It is a full numeric archive of every component in 329 published TMT games — 36 MB of source, each value traceable back to a file and a line number.

54.4% of the 13,746 real upgrades carry no effect() of their own at all. Their power is a branch inside the layer’s gainMult(). That is the single most common way a generated incremental game runs perfectly and does nothing.
generated, unwired
upgrades: {
  11: {
    effect()() { return new Decimal(2) },
    effectDisplay() { return format(this.effect()) }
  }
}

It loads. It sells. It prints ×2. Nothing in the game changes — and no rule anywhere fails.

what real games do
upgrades: {
  11: { unlocked() { return player.p.points.gte(1e6) } }
}

gainMult() {
  let ret = new Decimal(1)
  if (hasUpgrade("p", 11)) ret = ret.times(2)
  return ret
}

The upgrade is a token; the layer owns the arithmetic. Now the number is real — and the checker can prove it.

.pow()4,830

.log10()3,350
.times()1,652

Operations used by real upgrade effects, out of 6,274 upgrades that have one. Power and log shapes outnumber plain multipliers about three to one — so a generator that only ever emits ×2 produces something no human ships.

The bugs you only find by playing

One generated game was handed to a player. He reported three bugs. All three had the same shape — every part was individually reasonable, and the combination left a save that could not be recovered. Every one of the 53 rules at the time passed that game with zero failures. They check how things are wired and how big they are. None of them asked what survives a reset.

The engine prestiges straight from the game loop — if (tmp[layer].autoPrestige && tmp[layer].canReset) doReset(layer) — with no player toggle anywhere in that path. So automation a player cannot stop has to be safe by construction. The invariant: what auto-prestige requires must imply what makes the reset harmless. Miss it and the automation spends the currency its own safety milestone is priced in, so that milestone can never be bought and the wipe never stops.
found in 52 of 98 automated layers
autoPrestige() {
  if (hasMilestone(this.layer, 2)) return true
}
resetsNothing() {
  if (hasMilestone("sg2", 3)) return true
}

Auto-prestige turns on at milestone 2. The reset only stops hurting at sg2 M3 — 6.5 orders of magnitude later. In between, the layer wipes itself every single frame.

the same layer, repaired
autoPrestige() {
  if (hasMilestone(this.layer, 2) &&
      hasMilestone("sg2", 3)) return true
}
resetsNothing() {
  if (hasMilestone("sg2", 3)) return true
}

The automation now arrives later. That is the honest price of safety — and the checker proves the relation by comparing milestone sets, never their numbers.

What survives a reset

  • Milestones score on lifetime records, and the layer keeps them across an upper-row prestige
  • A layer with no doReset gets the engine’s default keep list — which holds neither best nor total
  • Version numbers are compared as text by the engine, so a downgrade silently rewrites every save

Counters are not prizes

  • Static layers need canBuyMax(), or every prestige banks exactly one floor
  • A static layer’s counter is its banked total — trickling into it earns less every second
  • Awards go through the engine so lifetime records stay honest

Then it caught a fourth

  • Those 53 rules had already been used to fix 24 defects in that same game
  • The new rules found a 25th the repair had missed: a layer with milestones but no doReset hook at all
  • Six of 104 layers had none — the repair checked every hook that existed, never the ones that didn’t

What "finished" means

A generated game ships only when every one of these holds. The rules come from measured corpus data and from real defects caught in earlier generated games.

Numbers

  • Requires ladders and cost curves taken from 329 measured games
  • First prestige within minutes; endgame reachable, never instant
  • Cost ladders span the measured 6+ orders of magnitude
  • Self-scaling effects budgeted so gains cannot compound out of control

Content

  • The theme decides tree topology, currencies, and hard caps
  • Effect-kind quotas prevent walls of identical flat multipliers
  • Microtabs organize layers before they become scroll walls
  • Challenges, clickables, and active loops land per blueprint quota

Verification

  • 58 static checks pass before manual testing starts
  • Zero console errors across the whole playthrough
  • Saves, offline cap, and the win screen verified by hand
  • Every effect is proven to be consumed by a formula somewhere
  • Prestige a high row with milestones earned, then confirm the ladder survived the reset
  • Rules hardened by six full games, a 329-game corpus, and the engine author's own design notes
